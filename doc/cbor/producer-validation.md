# Producer validation

## Rust producer verification, 2026-09-25

The reference producer now lives in the ddccontrol repository and shares the
XML decoder, format validator and deterministic encoder with its Rust reader.
The database repository pins its source revision and Rust toolchain in `.ci/`.
See [the producer workflow](producer.md) for local and offline use.

Reproduce the database integration checks using an installed or locally built
executable:

```sh
make check-cbor DDCDBGEN=/absolute/path/to/ddccontrol-dbgen
```

This checks:

* Exact generation of the immutable base CBOR and source manifest from frozen
  XML, and exact typed JSON dumps of all three complete fixtures.
* Lossless rewrites of the base, newer-database and future-description fixtures.
  The future required descriptor produces a guarded sidecar prohibiting XML
  fallback; the other fixtures retain their original source manifests.
* Conversion and validation of every maintained profile, with no `NOCHECKDB`
  exclusions. Repeated conversion from unrelated working directories under
  four locale settings must produce identical CBOR and manifest bytes.
* XML generation failure removes stale requested outputs; malformed CBOR fails
  validation and cannot publish a rewritten database.
* CI revision pins reject branches, abbreviated SHAs and shell expressions;
  Rust toolchain pins reject moving channels, suffixes and extra lines.

CI also runs the pinned producer/shared-format Rust tests and compares actual
XML and CBOR monitor trees, CAPS changes and success/failure across three CAPS
inputs and strict/tolerant modes for every profile. This catches semantic errors
that encode/decode roundtrips alone cannot find. Codec rejection vectors,
legacy encoding and numeric grammar, extension isolation, unknown-node fallback
guards, and frozen-reader compatibility are maintained in ddccontrol. Its
independent CDDL checker remains separate from the shared producer/reader codec.

No frozen XML, CBOR, JSON or snapshot expectation is regenerated by these
checks. No test sends a command to a physical monitor.

Executed locally against producer commit
`ef3447e475706b910daffa29c5f0dc86a5cd5a53`
([ddccontrol #338](https://github.com/ddccontrol/ddccontrol/pull/338)):

* `make check-cbor` passes with the actual static x86_64 musl executable built
  using Rust 1.85.0. The complete database and snapshot match the historical
  bytes below exactly.
* All 28 producer/shared-format tests pass on current Rust and Rust 1.77,
  including the full source attribute/order audit. The application's complete
  XML/CBOR differential check passes all 2,820 scenarios.
* `./configure --prefix=/usr` and `make -j4 check check-controls` pass, including
  all 470 profiles and 51 existing checker regression subtests.
* ShellCheck, Actionlint and independent review pass. The application's frozen
  first-reader, independent CDDL, production gettext, static release archive
  and actual s390x execution checks also pass; details are recorded there.

## Historical source baseline

The previous producer validation at `ddccontrol-db` source baseline `c4f616e`
(`VERSION=20260922`) counted 470 monitor XML files and 1,099,802 exact manifest
input bytes after generating `options.xml`. It generated 313,219 CBOR bytes,
with source snapshot:

`dbb9f1542128e579f61dc8147c03c2f72eb5220d0c31e7961c001516942656b9`

and full-file SHA-256:

`8315983f0ca09e8230e3cbb92b71e4cb5f0fa780634fa33a47179eb4ce36c813`.

The Rust replacement must preserve those bytes for that same source/revision.
Architecture execution and runtime memory/timing measurements belong to the
companion reader's validation report; file size does not establish RAM usage.
This remains an unpublished format candidate with the standards and coverage
gaps recorded in [sources](sources.md) and [coverage](coverage.md).
